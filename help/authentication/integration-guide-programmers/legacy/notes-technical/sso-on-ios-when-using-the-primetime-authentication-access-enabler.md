## 概要

Adobe Pass Authenticationを活用したアプリ間のシングルサインオン（SSO）は、基盤となるオペレーティングシステムに応じて異なる方法で機能します。

このドキュメントでは、Adobe Pass Authentication **Access Enabler**&#x200B;を使用する場合の、iOS **の** SSOについて説明します。

**Access Enabler** **1.10**&#x200B;は、Adobe Pass Authentication iOS ネイティブ SDKの最新バージョンです。 Adobeでは、古いバージョンに留まらず、このバージョンに移行することを強くお勧めします。 古いバージョンのAccess Enablerを使用している場合は、最新バージョン [ここ](https://tve.zendesk.com/hc/en-us/articles/204963209-iOS-Native-AccessEnabler-Library)をダウンロードできます。

IOSのSSOは、次の条件によって決定されます。

- アプリは、同じ&#x200B;**トークンストレージ**&#x200B;を使用する必要があります（Access Enablerによって作成されたカスタムペーストボードの形式）。
- アプリは同じ&#x200B;**Device ID**&#x200B;を生成する必要があります（Access Enablerは、OS バージョンに応じて、MAC アドレスまたはIDFVに基づいてDevice IDを計算します）。

## 動作

SSOの動作は次のとおりです。

- **iOS 6以前**:SSOは、同じチームまたは異なるチームによって開発されたアプリ間で自動的に動作します。 デバイス IDは、MAC アドレス（すべてのアプリで同じ値が生成されます）に基づいて計算され、ストレージ領域はすべてのアプリに共通です（カスタムペーストボードはiOS 6以前のアプリ間で共有可能です）。
  - **重要：** iOS SDK 1.9.4 リリースでは、iOS デプロイメントの最小目標が[iOS 7に増加しました。](https://tve.zendesk.com/hc/en-us/articles/204963209-iOS-Native-AccessEnabler-Library)
- **iOS 7以降**: SSOは次の条件で動作します。

1. アプリは、同じApple配布プロファイル、または同じチームに属するプロファイルを使用して公開されます。 これは、アプリがiOS 7以降でカスタムペーストボードを共有する唯一の方法です。 他のすべてのシナリオでは、ペーストボードはアプリケーションごとにサンドボックス化されます。 [*https://developer.apple.com/library/IOs/releasenotes/General/RN-iOSSDK-7.0/index.html*](https://developer.apple.com/library/ios/releasenotes/General/RN-iOSSDK-7.0/index.html)から：\+\[`UIPasteboard pasteboardWithName:create:\`]と+\[`UIPasteboard pasteboardWithUniqueName`\]は、同じアプリケーショングループ内のアプリのみがペーストボードにアクセスできるように、指定された名前を一意にしました。 開発者が既に存在する名前を持つペーストボードを作成しようとし、同じアプリスイートに含まれていない場合、独自のプライベートペーストボードが取得されます。 これは、システムが提供するペーストボード、一般、検索には影響しません。

1. アプリには同じバンドル ID プレフィックスがあります（最後のコンポーネントを除くすべてのコンポーネント）。 同じバンドル ID プレフィックスを共有するアプリケーションのみが、同じIDFVを計算します。 [*https://developer.apple.com/library/ios/documentation/UIKit/Reference/UIDevice\_Class/index.html\#//apple\_ref/occ/instp/UIDevice/identifierForVendor*](https://developer.apple.com/library/ios/documentation/UIKit/Reference/UIDevice_Class/index.html#//apple_ref/occ/instp/UIDevice/identifierForVendor)から：IOS 7では、最後のコンポーネントを除くバンドルのすべてのコンポーネントを使用してベンダーIDを生成します。 バンドル IDが1つのコンポーネントのみを持つ場合は、バンドル ID全体が使用されます。

次に、**&#39;iOS 7以降&#39;** シナリオに注目します。これは、実際のユーザーにとって最も頻繁なシナリオです。

両方の条件（同じ開発チームからプロファイルを共有し、共通のバンドル識別子のプレフィックスを持つ）は、SSOの必須の条件です。

以下に、可能な組み合わせとその結果を示します。

- **同じチームのプロファイルと同じバンドル ID プレフィックス**：アプリは同じペーストボードストレージを共有し、同じデバイス ID （IDFV）を持ちます。 ユーザーは（最初に使用したアプリで） 1回だけ認証する必要があり、認証状態は他のすべてのアプリで共有されます。 フローの例：

1. ユーザーがアプリ Aを開き（バンドル ID *com.x.y.AppA*）、未認証です
1. ユーザーはアプリ Aで認証を実行します
1. ユーザーはアプリ B （バンドル ID *com.x.y.AppB*）を開き、アプリから使用権限データを共有することで自動的に認証されます
A （手順2から）
1. ユーザーがアプリ Aを開き、まだ認証されている（手順2から）



- **同じチームのプロファイルでバンドル ID プレフィックスが異なる**：アプリは同じペーストボードストレージを共有しますが、デバイス ID （IDFV）が異なります。 利用者は、各アプリごとに1回認証する必要があります。 フローの例：

1. ユーザーがアプリ Aを開き（バンドル ID *com.x.y.AppA*）、未認証です
1. ユーザーはアプリ Aで認証を実行します
1. ユーザーはアプリ B （バンドル ID *com.z.AppB*&#x200B;を使用）を開き、Access Enablerは最初のアプリで取得したトークンを検出しますが（ストレージが共有されているため）、デバイス IDが異なるため、SSO経由で使用しようとしません
1. ユーザーはアプリ Bで認証を実行します
1. ユーザーがアプリ Aを開き、まだ認証されている（手順2から）



- **異なるチームのプロファイル （バンドル IDはこのシナリオでは無関係）**: アプリには異なるペーストボードストレージがあり、アプリ間のSSOは無効になります。 ユーザーは各アプリごとに1回認証する必要があり、アプリを切り替える際に認証セッションは永続的に維持されます。 フローの例：


1. ユーザーがアプリ Aを開き、未認証です
1. ユーザーはアプリ Aで認証を実行します
1. ユーザーがアプリ Bを開き、未認証です
1. ユーザーはアプリ Bで認証を実行します
1. ユーザーがアプリ Aを開き、認証されます（手順2から）
1. ユーザーがアプリ Bを開き、認証されます（手順4から）

**注：** **Apple App Store**&#x200B;を介してアプリケーションをインストールする場合、上記のSSOの条件が適用されることに注意してください。 アプリがシミュレーターにデプロイされている場合（アプリ署名が適用されない場合）、Xcodeでインストールされている場合、またはアドホックプロファイルを介して配布されている場合は、異なる結果が得られる可能性があります。

**重要：**&#x200B;注意（**AccessEnabler v1.8**&#x200B;に関して）：上記の2番目のシナリオ（同じチームのプロファイルですが、バンドル ID プレフィックスが異なる）は、同じチーム（メディア企業）によって開発されたアプリケーションで&#x200B;**AccessEnabler v1.8**&#x200B;のユーザーにとって非常に不快なユーザーエクスペリエンスを作成します。 ユーザーは、同じメディア企業からアプリケーション間を移行する際に自動的にログアウトするため、アプリケーション開発者はバンドル IDと配信プロファイルを決定する際に注意する必要があります。 この場合の正確なシナリオを以下に示します。

アプリは同じペーストボードストレージを共有しますが、デバイス ID （IDFV）が異なります。 ユーザーは各アプリごとに1回認証する必要がありますが、**アプリを切り替えると認証セッションが消去されます**。 フローの例：

1. ユーザーがアプリ Aを開き（バンドル ID *com.x.y.AppA*）、未認証です
1. ユーザーはアプリ Aで認証を実行します
1. ユーザーがアプリ B （バンドル ID *com.z.AppB*&#x200B;を使用）を開くと、アプリ Aによって作成された使用権限データは、アクセス イネーブラ（アプリ Bで現在計算されているデバイス IDと、使用権限トークンに保存されているデバイス IDとの間の競合を検出するセキュリティ メカニズム – アプリ Aによって作成）によって自動的に消去されます
1. ユーザーはアプリ Bで認証を実行します
1. ユーザーがアプリ Aを開くと、アプリ Bによって作成された使用権限データは、Access Enabler （アプリ Aで現在計算されているデバイス IDと、使用権限トークンに保存されているデバイス IDとの間の競合を検出するセキュリティ メカニズム – アプリ Bによって作成される）によって自動的に消去されます
